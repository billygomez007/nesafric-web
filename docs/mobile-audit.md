## 4. Authentication and isolation

- **Server authority.** The server is authoritative: the app shows only workspaces and homes the server lists, and hides nothing it relies on for security.
  - `x-organisation-id` is only ever taken from a server list, never from a route parameter.
- **Query cache.** Keys are `["account", userId, …]`.
  - Everything under them is removed on sign-out and on session expiry.
  - Opening a different workspace or home drops the previous one's cached data.
- **Stored data.** No offline store, background refresh, push or deep links carry account data.

### Security finding (fixed separately)

Tenant users could read internal maintenance data for their own requests via:
- `GET /api/maintenance/requests/:id`
- `GET /api/maintenance/tenants/:id/history`
- the create response

The exposed data covered staff notes and metadata, approvals, work-order costs, payment and ledger references, assignees and attachment storage keys.

- **Fix:** tenant callers now get an explicit tenant-safe view. Staff responses are unchanged.
- **Where:** hotfix PR #13 to `main`, which this slice also carries.

## 5. Tenant maintenance slice (this change)

- **Backend.** `GET /api/account/tenancies` is read-only.
  - It returns the caller's own non-archived tenant links in non-archived organisations, with their ACTIVE/EXPIRING leases: property and unit ids and names, and dates.
  - It returns no contact details, notes or amounts, and grants nothing.
  - Maintenance access is still checked per request, against the tenant link and the current lease.
- **Mobile screens:**
  - Account → **Your homes**.
  - Home screen: leases plus open and finished repair requests.
  - Request detail: status timeline and repair progress.
  - **Report a problem** form: home, category from the server enum, title, description, priority. It validates client-side with the server's limits.
- **Duplicate submissions.** Only one submission can be in flight. After an unclear failure (offline, timeout or 5xx) the button becomes "Send anyway" and the tenant is told to check their requests first, because the server has no idempotency key for maintenance creation.

## 6. Known gaps and next slices

1. **Maintenance, remaining parts:**
   - Photo attachments need a tenant upload contract; the app offers no photo upload yet.
   - Tenant comments: the notes endpoint is staff-only.
   - Completion confirmation is a staff transition.
   - An idempotency key for maintenance creation.
2. **Tenant: rent due, payments and receipts.** Use the payment routes' existing tenant checks. Guard against duplicate payments with idempotency keys.
3. **PM: properties and units (read), then maintenance triage.** Manager flow: triage, assign, approve cost.
4. **Provider:** assigned jobs, quotation submission, work-order updates.
5. **Push notifications:** `expo-notifications` plus a server-side device-token model.
6. **Stack sync:** merge `main` into #7→#11 once production is confirmed to serve `e3a5625`.
